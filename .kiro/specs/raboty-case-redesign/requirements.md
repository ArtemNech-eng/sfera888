# Requirements — Object-first redesign of `/raboty/[slug]`

## Introduction

Текущая страница кейса (`artifacts/marketplace/app/raboty/[slug]/page.tsx`) построена как «editorial article»: одна крупная обложка → narrative-описание → автор → отзыв → калькулятор → форма заявки в правом sticky-aside. Это marketplace-логика «найди мастера → оставь заявку», которая противоречит концепции платформы.

Стратегическая концепция (план §22, Pinterest + Houzz + AirBnB):

> Главный товар платформы — РЕЗУЛЬТАТ РЕМОНТА. Заявка — это следствие того, что человеку понравился объект и он сказал «хочу такой же».

Новая страница должна устроиться как Houzz-style product detail: **объект — герой**, заявка — производное в подвале. Воронка: **Вдохновение → Доверие → Хочу такой же → Заявка**.

Рефакторинг расщепляется на четыре итерации:

- **Iteration 1 (frontend-only)** — раскладка, чипы характеристик, крупный CTA, усиленный мастер-байлайн, форма уезжает в подвал. Использует существующие поля `master_portfolio` и `RabotyDetailResponse`.
- **Iteration 2 (backend)** — расширение схемы для сметы (работы / материалы / итого) и типа жилья.
- **Iteration 3 (backend)** — endpoint агрегации «средняя цена по похожим объектам».
- **Iteration 4 (Phase D)** — анонимное сохранение в избранное.

AI-дизайны (блок 6) — визуальный stub на старте, реальная Fal.ai-визуализация в Фазе 8 плана.

## Requirements

### 1. Galerija-first hero (Iteration 1)

**User story.** Как пользователь, попадающий на страницу кейса, я хочу сразу увидеть набор фото объекта, чтобы решить нравится ли мне результат, не читая текст.

**Acceptance criteria.**

1.1 КОГДА страница `/raboty/[slug]` загружается, ТОГДА первый блок под breadcrumbs ДОЛЖЕН отрисовать галерею:
   - главная hero-фотка (первое фото из `afterPhotos`) занимает левую часть, портретная или 4:5 ориентация
   - правее (или ниже на mobile) — сетка из 4-6 миниатюр (последующие `afterPhotos` + `beforePhotos`)
   - на mobile (`< sm`) галерея — горизонтальный snap-scroll контейнер

1.2 КОГДА у кейса меньше 4 фото, ТОГДА сетка миниатюр сжимается; если есть только 1 фото — рендерится одиночный full-bleed без сетки.

1.3 КОГДА у кейса нет ни одного фото, ТОГДА секция галереи скрывается полностью (отрисовка не ломается).

1.4 ВСЕ фото галереи ДОЛЖНЫ быть кликабельны и открывать lightbox для пошагового просмотра (в Iteration 1 — простой fullscreen overlay с next/prev, без zoom/pinch).

1.5 Текущий блок `<ArticleCover />` (16:9 одиночное фото) и блок `<BeforeAfterPair />` (две карточки 4:3) РАСФОРМИРОВЫВАЮТСЯ — их функция переходит в галерею. Before/after переезжает в отдельную секцию ниже (см. Requirement 11).

### 2. Inline characteristic chips (Iteration 1, расширение в Iteration 2)

**User story.** Как пользователь, я хочу видеть ключевые цифры объекта (площадь, бюджет, срок, город, услуга, тип жилья) в одной строке чипов сразу под фото, чтобы быстро оценить параметры.

**Acceptance criteria.**

2.1 КОГДА страница загружается, ТОГДА сразу под галереей ОТРИСОВЫВАЕТСЯ горизонтальная лента чипов с иконками:
   - 📍 город (`portfolio.city.name`)
   - 📐 площадь (`portfolio.area` м²)
   - 🕐 срок (поле появится в Iteration 2; в Iteration 1 — отсутствует)
   - 💰 бюджет (`portfolio.priceFrom` или диапазон)
   - 🔨 услуга (`portfolio.service.name`)
   - 🏢 тип жилья (новостройка / вторичка / частный дом / коммерция — поле появится в Iteration 2)

2.2 КАЖДЫЙ чип, у которого нет данных, СКРЫВАЕТСЯ — пустые «—» не показываем.

2.3 Чипы — server-rendered, no JS. Минимальная высота строки 40px на десктопе, на mobile — горизонтальный wrap с переносом.

2.4 (Iteration 2) ПОЛЕ срока: новая колонка `master_portfolio.duration_days INT NULL`. Редактор кейса в `/cabinet/portfolio/[slug]/edit` (см. Requirement 12) ПРИНИМАЕТ значение в днях. Чип отображает «N дней» с правильной плюрализацией (день / дня / дней).

2.5 (Iteration 2) ПОЛЕ типа жилья: новая колонка `master_portfolio.housing_type ENUM`. **Открытый вопрос D-1**: финальные значения enum — см. Open Questions.

### 3. Estimate breakdown (Iteration 2)

**User story.** Как пользователь, оценивающий бюджет, я хочу видеть из чего складывается сумма (работы + материалы), а не одну общую цифру, чтобы понять реалистично ли это для моего случая.

**Acceptance criteria.**

3.1 ОТДЕЛЬНАЯ секция «Смета объекта» появляется на странице после описания (см. Requirement 11), КОГДА мастер заполнил структурированную смету. Если смета НЕ заполнена — секция скрывается, остаётся только `priceFrom/priceTo` в чипах.

3.2 СЕКЦИЯ ОТРИСОВЫВАЕТ три строки:
   - **Стоимость работ**: сумма ₽
   - **Материалы**: сумма ₽
   - **Итого**: сумма ₽ (вычисляется или хранится)

3.3 Хранение сметы — структурированно. **Открытый вопрос D-2**: 3 отдельные колонки vs JSONB — см. Open Questions.

3.4 Если разработчик выбирает JSONB-форму, расширение в будущем (post-Iteration 2) ДОЛЖНО позволить добавить детализацию строк типа «электрика 12 000, штукатурка 18 000» без миграции.

3.5 Редактор кейса в `/cabinet/portfolio/[slug]/edit` ПРИНИМАЕТ работы/материалы как два отдельных числовых поля. Итог показывается в превью автоматически.

3.6 Валидация: если оба поля заполнены, итог не должен расходиться с `priceFrom` более чем на 10% (предупреждение мастеру в редакторе, не блокирующее).

### 4. Primary «Хочу такой же» CTA под фото (Iteration 1)

**User story.** Как пользователь, посмотревший фото и впечатлившийся, я хочу одним кликом сказать «хочу такой же» прямо на первом экране, не скроллив до конца страницы.

**Acceptance criteria.**

4.1 СРАЗУ под лентой чипов (Requirement 2) рендерится КРУПНАЯ кнопка-CTA:
   - текст: **«Хочу такой же»** (м.р., универсально для слова «ремонт»)
   - размер: высота не менее 56px на десктопе, full-width на mobile
   - цвет: brand green `var(--color-primary)`
   - под кнопкой — мелкая подпись: «Подберём мастеров, которые сделают похоже в вашем городе»

4.2 КЛИК по CTA скроллит к якорю `#lead-form` в подвале страницы (smooth scroll). Не модалка.

4.3 Кроме этой основной CTA, НА СТРАНИЦЕ нет дублирующих кнопок «Хочу такой же» в верхней половине (старая кнопка в `ArticleStatsBar` удаляется).

4.4 Sticky-вариант CTA: на десктопе при скролле вниз, КОГДА основная кнопка выходит из viewport, в правом верхнем углу появляется компактный sticky-pill «Хочу такой же» — фиксированный, минималистичный. На mobile — sticky-bar внизу экрана.

4.5 Фразеология «также» (слитно — «дополнительно») запрещена в копи кнопки. Только «такой же» (раздельно — «одинаковый»).

### 5. Сильный мастер-байлайн (Iteration 1)

**User story.** Как пользователь, увидевший понравившийся ремонт, я хочу понять кто это сделал — имя, рейтинг, сколько работ опубликовано, сколько объектов завершил, где работает — чтобы оценить надёжность автора, прежде чем нажать «Хочу такой же».

**Acceptance criteria.**

5.1 БЛОК мастера ОТРИСОВЫВАЕТ:
   - 👤 имя/публичный титул (`master.publicTitle` или `master.alias`)
   - аватар (или инициалы)
   - ⭐ рейтинг (`master.publicRating`) с формой «4.8 (132 отзыва)»
   - 📸 N работ — **число опубликованных кейсов** мастера (`portfolio.length` из API ответа `/master/[slug]`, либо передавать в `RabotyDetailResponse`)
   - 🏠 N завершённых — `stats.completedOrders`
   - 📍 город (`master.city`)
   - кнопка «Смотреть все работы →» — ведёт на `/master/[slug]`

5.2 Цифры (5.1) рендерятся в виде четырёх ячеек 2×2 на mobile / 4×1 на desktop, под именем + рейтингом.

5.3 Если у мастера 0 опубликованных кейсов или 0 завершённых заказов — соответствующая ячейка скрывается, но имя + рейтинг + город остаются обязательны.

5.4 BACKEND: API `/api/marketplace/raboty/[slug]` (метод `fetchRabotyCase`) ДОЛЖЕН возвращать `master.portfolioCount` и `master.completedOrders` в составе `RabotyDetailResponse`. **Не делать N+1**: добавить агрегаты в один SQL-запрос текущего endpoint.

### 6. Похожие объекты (Iteration 1, polish)

**User story.** Как пользователь, листающий вдохновение, я хочу после кейса увидеть похожие — чтобы продолжить просмотр, не возвращаясь в каталог.

**Acceptance criteria.**

6.1 СУЩЕСТВУЮЩИЙ блок `<SimilarCases />` ПЕРЕНОСИТСЯ выше — между описанием и AI-дизайнами (см. Requirement 11).

6.2 Карточки похожих ОБНОВЛЯЮТСЯ — используется единый `<CaseCard />` (как на главной и в `/raboty`), не локальный `<SimilarCard />`. Удалить дубликат.

6.3 Логика подбора похожих остаётся текущая backend (по `service_type_id` + диапазон площади). При нехватке (<3) — секция скрывается полностью.

6.4 КОПИ заголовка: «Похожие ремонты» (вместо «Возможно, вам также понравится»).

### 7. Market-average price block (Iteration 3)

**User story.** Как пользователь, увидевший цену конкретного кейса, я хочу понять — это дёшево, средне или дорого относительно рынка — чтобы откалибровать ожидания и довериться платформе.

**Acceptance criteria.**

7.1 СЕКЦИЯ «Сколько стоят такие ремонты» появляется на странице ПОСЛЕ блока «Похожие объекты», когда есть данные для агрегации.

7.2 СЕКЦИЯ ОТРИСОВЫВАЕТ:
   - заголовок типа «Ремонты ванной 4-6 м² в России»
   - две метрики:
     - **Средняя цена**: «от X ₽ до Y ₽» (P25–P75 или min/max от похожих кейсов)
     - **Базис**: «На основе N объектов»
   - дополнительно — «В вашем городе»: те же метрики, отдельной строкой (если выбрано из geo-IP или у пользователя есть city-cookie)

7.3 BACKEND: новый endpoint `GET /api/marketplace/raboty/market-stats?serviceSlug=…&areaMin=…&areaMax=…&citySlug=?`:
   - возвращает `{ russia: { p25, p75, count }, city: { p25, p75, count } | null }`
   - источник: агрегация `master_portfolio` где `is_published=true` и фильтры совпадают
   - кешируется на 1 час (cron-warmup для топ-комбинаций)

7.4 Если `count < 5` для России И `count < 3` для города — секция скрывается полностью (статистика недостоверна).

7.5 «Похоже» определяется как: тот же `service_type_id` + площадь в диапазоне `target ± 30%`. **Открытый вопрос D-3** — добавлять ли фильтр по style/housing_type — см. Open Questions.

### 8. AI-design suggestions block (Iteration 1 — stub, реальная реализация — Фаза 8)

**User story.** Как пользователь, увидевший понравившийся кейс, я хочу попробовать «примерить» этот стиль на свою комнату через AI-визуализацию.

**Acceptance criteria.**

8.1 БЛОК «Похожие идеи дизайна» появляется ПОСЛЕ Market-average (Requirement 7).

8.2 В Iteration 1 — три пресета стилей в виде карточек:
   - «Современный»
   - «Минимализм»
   - «Лофт»
   Каждая карточка — фото-stub (Unsplash CC0) + название стиля + кнопка «Попробовать».

8.3 КЛИК по карточке ведёт на `/dizajn/new?style=<slug>&room=<service-slug>` (preset URL — для последующей AI-генерации).

8.4 В Iteration 1 — `/dizajn/new` рендерит существующий design_waitlist форму (или ту, что мы построим в Фазе 8). Карточки на странице кейса не зависят от готовности этой формы — это просто deep-link.

8.5 (Phase 8) Когда AI-визуализация заработает — карточки заменяются реальными примерами для текущего room.

### 9. Save / Share (Iteration 1 — Share, Iteration 4 — Save)

**User story.** Как пользователь, увидевший понравившийся объект, я хочу сохранить его в подборку или поделиться ссылкой с супругой.

**Acceptance criteria.**

**Iteration 1:**

9.1 РЯДОМ с CTA «Хочу такой же» (Requirement 4) — две вторичные кнопки-иконки:
   - ❤️ «Сохранить» — в Iteration 1 рендерится как **disabled placeholder** с подписью «Скоро» (или прячется до Iteration 4)
   - 📤 «Поделиться» — клик использует Web Share API (`navigator.share`) на mobile / fallback к copy-to-clipboard на desktop
   - Поделиться — функциональна сразу, save — отложена

**Iteration 4:**

9.2 ПОЛЕ `master_portfolio.save_count INT NOT NULL DEFAULT 0`. Инкремент при сохранении пользователем.

9.3 НОВАЯ таблица `user_saves`:
   - анонимные сохранения по cookie-id (`kiro_anon_id`, UUID v4 в HTTP-only cookie)
   - привязка `(anon_id OR user_id) + portfolio_id`
   - **Открытый вопрос D-4**: claim-flow при логине — см. Open Questions.

9.4 КЛИК по ❤️ «Сохранить»:
   - оптимистично переключает иконку на «filled»
   - POST `/api/marketplace/raboty/[slug]/save` (toggle)
   - инкремент/декремент `save_count` атомарно
   - rate-limit: 30 сохранений в минуту с одного anon_id

9.5 НОВАЯ страница `/izbrannoe`:
   - читает `user_saves` по anon-id из cookie
   - рендерит сетку `<CaseCard />` с сохранёнными объектами
   - empty state: «Здесь будут сохранённые ремонты»

9.6 На карточке `<CaseCard />` — иконка ❤️ в правом верхнем углу с реальным состоянием (saved/unsaved). Текущая «hover only»-affordance заменяется на always-visible counter.

### 10. Lead form в подвале страницы (Iteration 1)

**User story.** Как пользователь, увидевший объект и принявший решение, я хочу оставить заявку в финальном блоке страницы — после того как я узнал всё об объекте, мастере и сравнил с рынком.

**Acceptance criteria.**

10.1 ТЕКУЩИЙ sticky-aside с формой в правой колонке УДАЛЯЕТСЯ. Форма переезжает в полноширинный блок ВНИЗУ страницы (после AI-designs, перед «Похожие работы» — см. Requirement 11).

10.2 БЛОК с формой ОТРИСОВЫВАЕТ:
   - eyebrow «Заявка автору»
   - заголовок «Хочу такой же»
   - подпись: «Уйдёт автору работы первой. Если не возьмёт за 30 минут — передадим похожим мастерам в вашем городе.»
   - три bullet-line с контекстом референса (услуга, город, площадь)
   - сама `<LeadForm />` с `attachedMasterId={master.id}` + `attachedMasterTitle={masterName}` (привязка к автору сохраняется — приоритет 30 минут)
   - якорь `#lead-form` (для скролла из CTA в Requirement 4)

10.3 Содержание копи в подписи СОХРАНЯЕТСЯ как сейчас в HEAD. Логика «автор первый, broadcast после 30 минут» backend-стороне реализуется в отдельной задаче (Plan §11.7, не входит в этот спек).

10.4 Forme больше НЕ sticky — на десктопе и mobile одинаково статична внизу.

### 11. Section ordering (Iteration 1, расширяется по итерациям)

**User story.** Как пользователь, я хочу чтобы страница вела меня по правильному пути: вдохновение → доверие → хочу такой же → заявка.

**Acceptance criteria.**

11.1 ПОРЯДОК секций на странице (после header/breadcrumbs) — **зафиксирован пользователем**:

```
1. Фото         (Gallery, Req 1)
2. Цена         (Inline chips с городом / площадью / сроком / бюджетом / услугой / типом жилья, Req 2)
3. Хочу такой же  (Primary CTA + Save/Share, Req 4 + 9.1)
4. До / После
5. Описание
6. Смета         (Estimate breakdown, Req 3 — Iteration 2; скрывается до заполнения)
7. Мастер        (Master byline, Req 5)
8. Похожие объекты (Similar, Req 6)
9. Похожие дизайны (AI-design stub, Req 8)
10. Заявка       (Lead form, Req 10)
```

11.1.a SUPPORTING-блоки, не входящие в основной 10-step funnel:
- **Market average** (Req 7, Iteration 3) — вставляется между «Похожие объекты» и «Похожие дизайны». Скрыт пока недостаточно данных (`<5` объектов в России).
- **Отзыв клиента** (existing `<ClientReview />`) — если есть, рендерится после «Описание» как pull-quote, до «Сметы». Если отзыва нет — секция отсутствует.

11.2 Между секциями ОТСТУПЫ соразмерны: 64px на mobile, 96px на desktop. Рамок и border-выделений минимум — visual rhythm через whitespace.

11.3 Sticky CTA pill (Requirement 4.4) появляется при скролле через секции 4–9 и исчезает при достижении секции 10 (форма уже видна).

### 12. Operator/master content — editor changes (Iteration 2)

**User story.** Как мастер, я хочу заполнить новые поля кейса (срок, тип жилья, смета) в редакторе кабинета.

**Acceptance criteria.**

12.1 РЕДАКТОР `artifacts/marketplace/app/cabinet/portfolio/[slug]/edit/page.tsx` ПОЛУЧАЕТ четыре новых поля:
   - срок (число, дни)
   - тип жилья (select из enum, см. Open Question D-1)
   - стоимость работ (число, ₽)
   - стоимость материалов (число, ₽)

12.2 Поля опциональные, но в превью кейса есть подсказка «Заполните смету — кейс получит +30% просмотров» (мотивация мастера).

12.3 ВАЛИДАЦИЯ:
   - срок: 1–365 дней
   - стоимость работ + материалов: 0–10 000 000 ₽ каждое
   - предупреждение если итог расходится с `priceFrom` более чем на 10%

12.4 BACKEND (api-server) принимает новые поля в `PUT /api/master-pwa/portfolio/[id]` — миграция схемы Drizzle, валидация Zod.

### 13. SEO / JSON-LD (Iteration 1, расширения в 2-3)

**User story.** Как поисковик, я хочу видеть структурированные данные о ремонте (картинки, цена, локация) для богатого превью в выдаче.

**Acceptance criteria.**

13.1 СУЩЕСТВУЮЩИЙ JSON-LD `caseJsonLd` РАСШИРЯЕТСЯ:

## Decisions (зафиксированы для Design phase)

Решения приняты по моим рекомендациям; могут быть пересмотрены точечно при необходимости.

**D-1. Тип жилья — enum из 4 значений.**
`housing_type ENUM('novostroyka','vtorichka','chastnyy_dom','kommerciya')`. Минимальный enum покрывает >95% случаев, типизация и фильтрация в каталоге работают чисто. Расширение позже без миграции невозможно — для него заведём отдельную задачу.

**D-2. Хранение сметы — JSONB `estimate`.**
Колонка `master_portfolio.estimate JSONB NULL` со схемой:
```ts
{
  works: number;              // ₽
  materials: number;          // ₽
  total?: number;             // вычисляется на фронте если null
  breakdown?: {label: string, cost: number}[];  // зарезервировано для Phase 2 SEO-страниц
}
```
Парсинг через Zod schema на api-server. Один index по `((estimate->>'total')::int)` если потребуется сортировка/фильтрация в каталоге.

**D-3. Market-stats — service + area ±30%.**
Без фильтра по `housing_type` в v1 (низкий коверидж новой колонки на старте). Когда заполненность `housing_type` > 30% от каталога — отдельной задачей расширяем фильтр.

**D-4. Claim-flow для анонимных сохранений — авто-перенос на login.**
Минимум трения. Когда у пользователя в cookie `kiro_anon_id` есть N сохранений и он логинится — UPDATE `user_saves SET user_id = X WHERE anon_id = Y` атомарно в одной транзакции. Toast-уведомление после: «Перенесли N сохранённых ремонтов в ваш аккаунт».

**D-5. Lightbox — простой fullscreen overlay (Iteration 1).**
Next/prev кнопки + закрытие по Escape/клик-в-фон. Без zoom/pinch — это апгрейд post-Iter 1 если будет фидбэк.

**D-6. Sticky-CTA на mobile — bottom bar.**
Полноширинная плашка внизу экрана (`fixed bottom-0`) с кнопкой «Хочу такой же», появляется когда основная CTA вышла из viewport, исчезает при касании formy в подвале. На десктопе — pill в верхнем правом углу (как в Req 4.4).
