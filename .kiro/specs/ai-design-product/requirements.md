# Requirements Document

## Introduction

AI_Design_Product — это самостоятельная продуктовая линия на домене chestnye-mastera.ru, в которой пользователь по короткой форме (тип комнаты, размеры, стиль, бюджет) получает законченный дизайн-проект интерьера: 6 фотореалистичных ракурсов с сохранением идентичности комнаты, программный план вида сверху с размерами, 3D-isometric ракурс с выносками, подбор мебели из жёстко закодированного каталога, подбор отделочных материалов, реальную смету с городскими коэффициентами, цветовую палитру, набор дизайн-решений, длинное описание, итоговую инфографику и скачиваемый PDF на A4.

Стратегически продукт меняет роль AI-дизайна на сайте: раньше 50 заранее заготовленных проектов (Showcase_Project) рассматривались как SEO-воронка для перехода в каталог мастеров; теперь AI-дизайн становится самостоятельным товаром, который клиент покупает (на этапе MVP — получает бесплатно для валидации спроса). Маркетплейс мастеров и пользовательский UGC остаются отдельными продуктовыми линиями и в этом спеке не затрагиваются.

Существующая инфраструктура должна быть расширена, а не переписана: таблица `designs`, фоновый воркер `designWorker.ts`, обёртки Fal.ai (`falAi.ts`), GPT-генератор контента (`designContent.ts`), композитор инфографики (`infographicComposer.ts`), публичная страница `/dizajn/{slug}` (`DesignBoard.tsx`), R2 для ассетов, OpenAI-шлюз через OpenRouter, Postgres на Railway, идентификация анонимных пользователей через cookie `kiro_anon_id` (`anon_id` UUID v4). Все новые части (jsoн-планировщик, геометрический валидатор, программный 2D-план, выноски на 3D-isometric, подбор мебели и материалов из БД, реальная смета, PDF) встраиваются как новые шаги пайплайна `Design_Worker` и новые поля в `designs`.

Основной технический риск — Identity_Preservation: 6 ракурсов одной комнаты должны выглядеть как одна и та же комната с одинаковой палитрой, материалами и мебелью, а не как 6 разных интерьеров. Спек предписывает явный процесс выбора между FLUX Kontext Pro и текущей gpt-image-1.5 edit на основе измеримого критерия.

Отдельный продуктовый риск — стоимость генерации (~5–7 AI-вызовов, ориентир до Cost_Ceiling в $0.30 за проект). Спек требует ранний отказ при невалидном вводе и поддержку частичной деградации, чтобы не сжигать бюджет на запросах, которые всё равно нельзя завершить.

## Glossary

- **AI_Design_Product**: продуктовая линия, в рамках которой создаётся `Design_Project` по форме на сайте.
- **Design_Project**: одна запись в таблице `designs`, представляющая один дизайн-проект для одного помещения и доступная по публичному URL `/dizajn/{slug}`.
- **Design_Form**: публичная форма на странице `/ai-design` (или эквивалентной), без требования авторизации, через которую пользователь задаёт параметры будущего `Design_Project`.
- **Design_Worker**: фоновый воркер `artifacts/api-server/src/lib/designWorker.ts`, который раз в 5 секунд берёт одну запись `designs` со статусом `generating` и доводит её до `completed` или `failed`.
- **Layout_JSON**: промежуточный артефакт, выданный GPT, описывающий план комнаты в виде структурированного JSON со списком предметов мебели, их позициями (`x`, `y`, `rotation`) и габаритами (`width`, `depth`, `height`), позицией двери и окна.
- **Geometric_Validator**: модуль, который по введённым размерам комнаты и `Layout_JSON` проверяет, что мебель помещается в комнату, не пересекается между собой, не блокирует дверь и проходы между предметами не уже 60 см.
- **Furniture_Catalog**: жёстко закодированный каталог мебели в БД (~150 SKU для MVP, тип помещения — bedroom), с полями: SKU, название, бренд, цена в копейках, ширина, глубина, высота, тип, стилевые теги, ссылка в магазин-партнёр.
- **Finishing_Materials_Catalog**: жёстко закодированный каталог отделочных материалов в БД, разделённый на стены / пол / потолок / прочее, с ценой за м² или за единицу.
- **Hardcoded_Catalog**: общее обозначение для `Furniture_Catalog` + `Finishing_Materials_Catalog`. На MVP ведётся вручную; в будущей итерации заменяется парсером магазинов (Hoff / Leman PRO / Divan.ru / Lazurit), что в этом спеке не описывается.
- **Showcase_Project**: проект из 50 редакторских образцов, создаваемый оператором вручную в админ-CRM, а не пользователем через `Design_Form`. На MVP заморожен; модель данных должна поддерживать оба режима.
- **Real_Estimate**: смета `Design_Project`, рассчитанная как стоимость отделочных материалов по м² плюс цены выбранных SKU из `Furniture_Catalog` плюс стандартный коэффициент стоимости работ для города пользователя (если задан).
- **Identity_Preservation**: свойство пайплайна, при котором 6 фотореалистичных ракурсов одного `Design_Project` показывают одну и ту же комнату — те же стены, ту же мебель, ту же палитру, ту же отделку.
- **Hero_Render**: первый из 6 ракурсов (общий вид от двери), который генерируется text-to-image и потом используется как референс для остальных 5 ракурсов (edit-image).
- **Angle_Render**: каждый из ракурсов 2..6, получаемый edit-image вызовом с reference изображением Hero_Render.
- **Top_Down_Plan**: программно сгенерированная 2D-планировка вида сверху, отрисованная сервером в SVG из `Layout_JSON`, с подписями размеров стен и габаритов основной мебели.
- **Isometric_Render**: 3D-isometric изображение комнаты, поверх которого программно нанесены выноски с подписями ключевой мебели; координаты выносок берутся из `Layout_JSON`, а не зашиты в коде.
- **Color_Palette**: набор из 5 цветов в HEX, извлечённый программно из Hero_Render с помощью `lib/colorExtraction.ts`.
- **Infographic**: одно итоговое изображение 2048×1366 JPEG, собранное `infographicComposer.ts` из ракурсов, `Top_Down_Plan`, `Isometric_Render`, текстов и таблиц.
- **PDF_Document**: многостраничный A4 портретный PDF дизайн-проекта, скачиваемый со страницы `/dizajn/{slug}` по кнопке.
- **PDF_Renderer**: серверный модуль, рендерящий `PDF_Document` (через Puppeteer или PDFKit; конкретный выбор — задача дизайн-фазы).
- **AI_Image_Provider**: Fal.ai (модели FLUX dev img2img, FLUX Pro Ultra text2img, gpt-image-1.5 text-to-image, gpt-image-1.5 edit-image, FLUX Kontext Pro для пилота Identity_Preservation).
- **AI_Content_Provider**: OpenAI-шлюз через OpenRouter (используется для GPT-генерации `Layout_JSON`, h1/seoTitle/seoDescription/description/materials/estimate/solutions).
- **Anon_Id**: UUID v4 в cookie `kiro_anon_id`, существующий на сайте механизм идентификации анонимного посетителя; используется как владелец `Design_Project` без авторизации.
- **Fingerprint_Cookie**: cookie `kiro_anon_id`, содержащая `Anon_Id`.
- **Captcha_Provider**: внешний сервис проверки бота (Cloudflare Turnstile или hCaptcha; конкретный выбор — задача дизайн-фазы), вызываемый перед созданием `Design_Project`.
- **Rate_Limiter**: модуль, ограничивающий количество новых `Design_Project` в сутки на один IP-адрес и на один `Anon_Id`.
- **Cost_Ceiling**: ориентир суммарной стоимости AI-вызовов на один `Design_Project`, $0.30 USD; используется как budget-guard при принятии решения о повторных попытках и частичной деградации.
- **Generation_Pipeline**: последовательность шагов внутри `Design_Worker` для одного `Design_Project`: GPT-генерация `Layout_JSON` → `Geometric_Validator` → 6 ракурсов AI (Hero + 5 Angle) → `Top_Down_Plan` → `Isometric_Render` → детальные кропы (sharp) → подбор мебели → подбор материалов → `Real_Estimate` → `Color_Palette` → AI-текст (h1/seoTitle/seoDescription/description/solutions) → `Infographic` → `PDF_Document`.
- **Generation_Status**: значение поля `designs.status`, одно из `draft`, `generating`, `completed`, `failed`, `private`.
- **Generation_Progress**: значение поля `designs.progress` (0..100), отражающее долю выполненных шагов `Generation_Pipeline`.
- **Public_Page**: страница `/dizajn/{slug}`, рендерящая `Design_Project` для всех пользователей, в том числе анонимных.
- **My_Designs_List**: список всех `Design_Project`, принадлежащих текущему `Anon_Id`, доступный без авторизации.

## Requirements

### Requirement 1: Создание Design_Project через публичную форму

**User Story:** Как анонимный посетитель сайта, я хочу через короткую форму на `/ai-design` запустить генерацию дизайн-проекта по моим параметрам, чтобы получить готовый проект для моей комнаты без регистрации.

#### Acceptance Criteria

1. THE Design_Form SHALL принимать поля: тип помещения, ширина в см, длина в см, высота в см, стиль, бюджет в рублях, опциональные флаги дополнительных функций (например, рабочая зона, акцентная стена).
2. THE Design_Form SHALL ограничивать тип помещения значениями `bedroom`, `kitchen`, `bathroom`, `living_room`, `hallway`, `nursery`, `apartment`.
3. WHILE текущая фаза MVP активна, THE Design_Form SHALL разрешать запуск генерации только для типа помещения `bedroom` и SHALL отображать остальные типы как «скоро» без возможности отправки.
4. THE Design_Form SHALL ограничивать стиль значениями `modern`, `scandinavian`, `loft`, `minimalism`, `neoclassic`, `japandi`, `classic`.
5. THE Design_Form SHALL принимать ширину и длину помещения в диапазоне от 200 см до 800 см и высоту в диапазоне от 220 см до 350 см.
6. THE Design_Form SHALL принимать бюджет в диапазоне от 50 000 ₽ до 5 000 000 ₽.
7. THE Design_Form SHALL отображать рядом с полями размеров типичные значения для выбранного типа помещения (например, для `bedroom` — «обычно 12–18 м²»), при этом не подставляя эти значения автоматически.
8. WHEN пользователь отправляет форму с валидными значениями всех полей и подтверждённой капчей (Requirement 3), THE API_Server SHALL создать запись в `designs` со статусом `generating`, заполненными полями `room_type`, `style`, `area`, `budget`, привязкой к текущему `Anon_Id` через `anon_id` и сгенерированным `slug`.
9. WHEN запись `designs` создана, THE API_Server SHALL вернуть пользователю `slug` и редиректить на `/dizajn/{slug}`.
10. IF любое поле формы выходит за допустимые границы, THEN THE API_Server SHALL вернуть ответ 400 с описанием каждого нарушения, не создавая запись в `designs` и не вызывая ни AI_Image_Provider, ни AI_Content_Provider.

### Requirement 2: Геометрическая валидация перед запуском AI-вызовов

**User Story:** Как владелец продукта, я хочу отказывать в генерации заведомо невозможных по размерам комнат до первого AI-вызова, чтобы не тратить деньги на проекты, которые `Geometric_Validator` всё равно отбракует.

#### Acceptance Criteria

1. WHEN форма успешно прошла базовую валидацию (Requirement 1) и до создания записи `designs`, THE API_Server SHALL вызвать `Geometric_Validator` с сухой проверкой минимальной площади для выбранного типа помещения.
2. THE Geometric_Validator SHALL хранить минимально допустимую площадь для каждого типа помещения: `bedroom` ≥ 6 м², `kitchen` ≥ 4 м², `bathroom` ≥ 2 м², `living_room` ≥ 8 м², `hallway` ≥ 1.5 м², `nursery` ≥ 6 м², `apartment` ≥ 18 м².
3. IF введённая площадь меньше минимально допустимой для выбранного типа помещения, THEN THE API_Server SHALL вернуть ответ 400 с человеко-читаемым сообщением «комната слишком мала для типа X» и SHALL не создавать запись `designs`.
4. WHEN `Design_Worker` получает Layout_JSON от AI_Content_Provider (Requirement 6), THE Geometric_Validator SHALL проверить, что для каждого предмета мебели его прямоугольник полностью лежит внутри прямоугольника комнаты.
5. THE Geometric_Validator SHALL проверять, что прямоугольники любых двух предметов мебели не пересекаются (с допуском ≤ 1 см).
6. THE Geometric_Validator SHALL проверять, что между любыми двумя предметами мебели и между любым предметом и стеной с дверью есть проход шириной не меньше 60 см вдоль пути от двери к каждому функциональному предмету помещения (для `bedroom` — кровати и шкафу).
7. IF Layout_JSON не проходит проверки 4–6, THEN THE Design_Worker SHALL запросить у AI_Content_Provider повторную генерацию Layout_JSON с описанием конкретных нарушений в подсказке, не более 2 повторов.
8. IF после 2 повторов Layout_JSON всё ещё не проходит проверки 4–6, THEN THE Design_Worker SHALL установить `designs.status` в `failed` с `error_message` «не удалось разместить мебель в заданных размерах», и SHALL не вызывать AI_Image_Provider для данного `Design_Project`.
9. THE Geometric_Validator MAY использовать более строгие минимальные площади, чем перечисленные в пункте 2 (например, 7 м² вместо 6 м² для `bedroom`), и SHALL не использовать значения ниже перечисленных в пункте 2.

### Requirement 3: Защита от злоупотреблений — Captcha и Rate_Limiter

**User Story:** Как владелец продукта, я хочу ограничить количество запусков `Design_Project` от одного посетителя за сутки, чтобы исключить ботов и сценарии, при которых стоимость AI-вызовов растёт неконтролируемо.

#### Acceptance Criteria

1. THE Design_Form SHALL встраивать виджет Captcha_Provider и SHALL не разрешать отправку формы без полученного капча-токена.
2. WHEN форма отправлена с капча-токеном, THE API_Server SHALL верифицировать токен у Captcha_Provider до любых других проверок ввода и SHALL отвергать запрос с ответом 400 при неверном или отсутствующем токене.
3. THE Rate_Limiter SHALL ограничивать количество успешных созданий `Design_Project` от одного IP-адреса значением 5 в сутки.
4. THE Rate_Limiter SHALL ограничивать количество успешных созданий `Design_Project` от одного `Anon_Id` значением 3 в сутки.
5. IF число успешных созданий за последние 24 часа достигло лимита по IP или по `Anon_Id`, THEN THE API_Server SHALL вернуть ответ 429 с сообщением «достигнут дневной лимит, попробуйте через N часов» и SHALL не создавать запись `designs`.
6. THE Rate_Limiter SHALL считать только запросы, дошедшие до создания записи `designs` (статус `generating`); отказы по валидации формы (Requirement 1.10) и по геометрии (Requirement 2.3) в лимит не попадают.
7. WHEN Design_Worker завершает `Design_Project` со статусом `failed` по причине превышения Cost_Ceiling (Requirement 14.5), THE Rate_Limiter SHALL считать этот запрос как использованный.

### Requirement 4: Анонимное владение и список «мои дизайны»

**User Story:** Как анонимный посетитель, я хочу видеть список всех дизайн-проектов, которые я создал в этом браузере, чтобы возвращаться к ним без регистрации.

#### Acceptance Criteria

1. WHEN запись `designs` создаётся (Requirement 1.8), THE API_Server SHALL записать `Anon_Id` текущего посетителя в поле `designs.anon_id`.
2. IF запрос на создание не содержит cookie `kiro_anon_id`, THEN THE API_Server SHALL сгенерировать новый `Anon_Id` (UUID v4), установить cookie `kiro_anon_id` со сроком жизни не менее 365 дней, обновить текущую серверную сессию так, чтобы она использовала новый `Anon_Id` (а не любой ранее ассоциированный идентификатор), и использовать новый `Anon_Id` как владельца записи.
3. THE API_Server SHALL предоставлять эндпоинт `GET /api/marketplace/dizajn/mine`, возвращающий все записи `designs` для текущего `Anon_Id`, отсортированные по `created_at` убыванию.
4. THE Public_Page SHALL для каждого `Design_Project`, у которого `anon_id` совпадает с текущим cookie, отображать пометку «ваш проект» и SHALL не показывать эту пометку для остальных посетителей.
5. WHILE `designs.anon_id` равен текущему `Anon_Id` пользователя, THE Public_Page SHALL отображать `Design_Project` независимо от значения `is_public`.
6. WHILE `designs.anon_id` не равен текущему `Anon_Id` AND `designs.is_public = false` AND `designs.status` ≠ `private`, THE Public_Page SHALL открывать `Design_Project` по прямой ссылке без авторизации, потому что владение анонимное и контролируется только знанием URL.
7. THE My_Designs_List SHALL включать для каждого `Design_Project` поля `slug`, `roomType`, `style`, текущий `status`, текущий `progress`, `resultImageUrl` и `createdAt`.

### Requirement 5: Асинхронная генерация со статусом и прогрессом

**User Story:** Как пользователь, ожидающий результата 3–5 минут, я хочу видеть на странице `/dizajn/{slug}` понятный индикатор прогресса и автоматическое обновление страницы, когда проект готов, чтобы не нажимать F5 вручную.

#### Acceptance Criteria

1. THE Design_Worker SHALL обрабатывать одну запись `designs` со статусом `generating` за один тик (текущий интервал 5 секунд), от старой к новой по `created_at`, и SHALL не подбирать записи в любом другом статусе (`draft`, `completed`, `failed`, `private`).
2. THE Design_Worker SHALL обновлять `designs.progress` после завершения каждого крупного шага Generation_Pipeline (`Layout_JSON` готов, Hero_Render готов, все Angle_Render готовы, Top_Down_Plan готов, Isometric_Render готов, кропы готовы, мебель подобрана, материалы и `Real_Estimate` готовы, `Color_Palette` готова, AI-текст готов, `Infographic` собрана, `PDF_Document` собран).
3. THE API_Server SHALL предоставлять эндпоинт, возвращающий по `slug` текущие `status`, `progress` и `error_message` записи `designs` в формате, совместимом с существующим `DesignFullDTO`.
4. WHILE `designs.status = generating`, THE Public_Page SHALL опрашивать API не реже одного раза в 3 секунды и SHALL отображать прогресс в виде шкалы с подписью текущего шага.
5. WHEN `designs.status` переходит в `completed`, THE Public_Page SHALL прекратить опрос и отрендерить полную страницу `Design_Project`.
6. WHEN `designs.status` переходит в `failed`, THE Public_Page SHALL прекратить опрос и отрендерить экран ошибки с человеко-читаемым `error_message` и предложением повторить попытку через форму.
7. WHILE запись `designs` находится в статусе `generating` дольше 10 минут, THE Design_Worker SHALL и срабатывать watchdog-ом, и переводить её в `failed` с `error_message = "stuck for over 10 minutes"`; обе части (срабатывание watchdog и переход статуса) SHALL обеспечиваться вместе, как уже реализовано.

### Requirement 6: Layout_JSON как промежуточный артефакт

**User Story:** Как разработчик пайплайна, я хочу, чтобы AI_Content_Provider возвращал план мебели в виде структурированного JSON, который можно проверить программно и использовать для отрисовки `Top_Down_Plan` и выносок на `Isometric_Render`, чтобы не зависеть от того, что нарисует image-модель.

#### Acceptance Criteria

1. THE Design_Worker SHALL запрашивать у AI_Content_Provider `Layout_JSON` через структурированный вывод (`response_format: json_schema`) с явной схемой.
2. THE Layout_JSON SHALL содержать поля: размеры комнаты в см (`width`, `length`, `height`), позицию двери (стена, смещение от угла, ширина), позицию окна (стена, смещение от угла, ширина) и массив `furniture` с предметами.
3. Каждый предмет мебели в `Layout_JSON` SHALL содержать `id`, `type` (например, `bed`, `wardrobe`, `desk`, `chair`, `nightstand`, `rug`), `width_cm`, `depth_cm`, `height_cm`, `x_cm`, `y_cm`, `rotation_deg`.
4. THE Design_Worker SHALL сохранять `Layout_JSON` в новое JSONB-поле записи `designs` (имя и миграция определяются в дизайн-фазе) для последующего использования при отрисовке `Top_Down_Plan`, выносок на `Isometric_Render` и при подборе мебели из `Furniture_Catalog`.
5. WHEN AI_Content_Provider возвращает структурно невалидный JSON, THE Design_Worker SHALL запросить повторную генерацию не более 2 раз, и при дальнейшей неудаче SHALL перевести `Design_Project` в `failed` с `error_message = "не удалось получить план комнаты"`.

### Requirement 7: Шесть фотореалистичных ракурсов с Identity_Preservation

**User Story:** Как пользователь, я хочу, чтобы все 6 ракурсов показывали одну и ту же комнату — те же стены, ту же палитру, ту же мебель, чтобы проект выглядел цельным, а не как 6 разных интерьеров.

#### Acceptance Criteria

1. THE Design_Worker SHALL генерировать ровно 6 фотореалистичных ракурсов для каждого `Design_Project`: общий вид от двери (Hero_Render), вид на главную мебель, вид на хранение, вид у окна, вид на акцентную стену, вид на потолок и освещение.
2. THE Design_Worker SHALL генерировать Hero_Render режимом text-to-image с подсказкой, основанной на `Layout_JSON`, типе помещения, стиле и габаритах.
3. THE Design_Worker SHALL генерировать каждый из 5 остальных ракурсов (Angle_Render) режимом edit-image с reference-изображением, равным Hero_Render, и описанием нужного угла обзора.
4. THE Design_Worker SHALL запускать генерацию 5 Angle_Render параллельно после готовности Hero_Render.
5. THE Generation_Pipeline SHALL поддерживать конфигурируемого AI_Image_Provider для шага edit-image со значениями `gpt_image_1_5_edit` и `flux_kontext_pro` через переменную окружения.
6. THE дизайн-фаза SHALL включать сравнительный пилот FLUX Kontext Pro vs gpt-image-1.5 edit на одной и той же выборке параметров и SHALL зафиксировать выбранное значение для MVP в записи решения; в пайплайне MVP используется выбранный провайдер.
7. IF генерация любого из 5 Angle_Render завершилась ошибкой, THEN THE Design_Worker SHALL повторить вызов один раз; при успехе повтора ракурс SHALL считаться успешным и SHALL не помечаться как отсутствующий; при второй неудаче ракурс SHALL быть исключён из массива `designs.views` (без записей-заполнителей), и пайплайн SHALL продолжаться, не блокируя завершение `Design_Project` (см. Requirement 14.2).
8. THE Design_Worker SHALL сохранять все успешно сгенерированные ракурсы в R2 и записывать их в массив `designs.views` в исходном порядке генерации (Hero_Render первым, затем Angle_Render по их номеру), пропуская позиции для не сгенерированных ракурсов и не вставляя на их место заполнителей.

### Requirement 8: Программный 2D-план вида сверху из Layout_JSON

**User Story:** Как пользователь, я хочу видеть точный план комнаты с размерами стен и габаритами мебели, отрисованный без AI, чтобы планировка была технически читаемой, а не «художественной».

#### Acceptance Criteria

1. THE Design_Worker SHALL отрисовывать `Top_Down_Plan` программно в SVG из `Layout_JSON`, без вызова AI_Image_Provider.
2. THE Top_Down_Plan SHALL отображать стены, дверь и окно по координатам из `Layout_JSON`.
3. THE Top_Down_Plan SHALL отображать прямоугольник для каждого предмета мебели в правильной позиции и с правильным поворотом.
4. THE Top_Down_Plan SHALL подписывать длины стен в сантиметрах и габариты главной мебели (для `bedroom` — кровати и шкафа).
5. THE Top_Down_Plan SHALL поддерживать набор шаблонов отрисовки на тип помещения; для MVP реализуется шаблон `bedroom`. WHILE тип помещения проекта равен `bedroom`, THE Design_Worker SHALL всегда использовать программную отрисовку и SHALL не вызывать AI_Image_Provider в качестве fallback, даже если шаблонная отрисовка завершилась ошибкой. Остальные типы помещения дают placeholder с подписью «вид сверху» (как уже сделано в `infographicComposer.ts`); IF генерация placeholder завершилась ошибкой, THEN THE Design_Worker SHALL продолжить пайплайн без визуального контента в блоке «Вид сверху» для соответствующего типа помещения.
6. THE Design_Worker SHALL сохранять отрисованный `Top_Down_Plan` как PNG/SVG в R2 и записывать ссылку в новое поле записи `designs` (имя поля определяется в дизайн-фазе).
7. THE Public_Page SHALL отображать `Top_Down_Plan` в блоке «Вид сверху» и SHALL заменять им любой существующий placeholder из `infographicComposer.ts` для типов помещения, у которых шаблон реализован.

### Requirement 9: Isometric_Render с программными выносками

**User Story:** Как пользователь, я хочу видеть 3D-аксонометрический ракурс с подписями к ключевой мебели, расположенными там, где эта мебель действительно находится в плане, чтобы выноски не «висели в воздухе».

#### Acceptance Criteria

1. THE Design_Worker SHALL генерировать аксонометрическое 3D-изображение комнаты через AI_Image_Provider с подсказкой, построенной из `Layout_JSON` и стиля, как в существующем `buildIsometricPrompt`.
2. THE Design_Worker SHALL программно накладывать на полученное изображение SVG-выноски с подписями к главной мебели (для `bedroom` — кровать, шкаф, прикроватные тумбы, рабочая зона).
3. WHEN `Layout_JSON` становится доступным, THE Design_Worker SHALL вычислять координаты концов выносок из `Layout_JSON` через изометрическую проекцию, а не зашивать их в коде, как сейчас в `buildIsometricCalloutsSvg`.
4. WHEN изометрический ракурс успешно сгенерирован, THE Design_Worker SHALL сохранять итоговый `Isometric_Render` (с выносками) в R2 и записывать его в `designs.views` (точная позиция определяется в дизайн-фазе для совместимости с `DesignBoard.tsx`); сохранение в R2 как `Isometric_Render` SHALL не выполняться при завершении других ракурсов и SHALL запускаться только для шага генерации изометрического ракурса.
5. IF генерация Isometric_Render завершилась ошибкой после 1 повтора, THEN THE Design_Worker SHALL пометить ракурс как отсутствующий и продолжить остальные шаги Generation_Pipeline без него (см. Requirement 14.2).

### Requirement 10: Подбор мебели из Furniture_Catalog

**User Story:** Как пользователь, я хочу видеть список реально продающихся предметов мебели, которые можно купить под этот проект, со ссылками в магазин-партнёр, чтобы проект был не только красивым, но и реализуемым.

#### Acceptance Criteria

1. THE API_Server SHALL содержать таблицу `furniture_products` с полями: `sku`, `name`, `brand`, `price_kopeks`, `width_cm`, `depth_cm`, `height_cm`, `type` (например, `bed`, `wardrobe`, `desk`, `chair`, `nightstand`), `style_tags` (массив), `room_types` (массив), `image_url`, `partner_url`, `is_available` (boolean), `created_at`, `updated_at`.
2. WHILE текущая фаза MVP активна, THE Furniture_Catalog SHALL содержать не менее 100 и не более 200 SKU с типом помещения `bedroom`; другие типы помещения остаются пустыми и заполняются в последующих итерациях.
3. WHEN Generation_Pipeline доходит до шага подбора мебели, THE Design_Worker SHALL для каждого предмета `type` из `Layout_JSON` выбрать из `Furniture_Catalog` SKU, удовлетворяющий условиям: `is_available = true`, `room_types` содержит тип помещения проекта, `style_tags` содержит выбранный стиль или совместимый, габариты SKU отличаются от габаритов из `Layout_JSON` не более чем на 15 см по каждой стороне.
4. THE Design_Worker SHALL ограничивать суммарную цену выбранных SKU долей от `designs.budget`, согласованной с распределением сметы (Requirement 11.3); при превышении SHALL заменять самые дорогие SKU на более дешёвые альтернативы из `Furniture_Catalog`, удовлетворяющие условиям 3.
5. IF для какого-либо предмета `type` из `Layout_JSON` не нашлось ни одного подходящего SKU, THEN THE Design_Worker SHALL пометить позицию как «не подобрано» и продолжить, не блокируя `Design_Project`.
6. THE Design_Worker SHALL сохранять подобранные SKU в новом JSONB-поле записи `designs` (имя определяется в дизайн-фазе), вместе с фактической ценой каждого SKU.
7. THE Public_Page SHALL отображать подобранную мебель в отдельном блоке с миниатюрой, названием, ценой и ссылкой `partner_url`; для позиций «не подобрано» SHALL показывать заглушку «уточняется».

### Requirement 11: Подбор отделочных материалов и Real_Estimate

**User Story:** Как пользователь, я хочу видеть смету проекта, рассчитанную из реальных цен на материалы по м² и реальных цен мебели, а не «среднее по больнице», чтобы понимать порядок затрат.

#### Acceptance Criteria

1. THE API_Server SHALL содержать таблицу `finishing_materials` с полями: `sku`, `name`, `brand`, `category` (`walls`, `floor`, `ceiling`, `other`), `unit` (`sqm` или `pcs`), `price_per_unit_kopeks`, `style_tags`, `room_types`, `partner_url`, `is_available`, `created_at`, `updated_at`.
2. WHEN Generation_Pipeline доходит до шага подбора материалов, THE Design_Worker SHALL для каждой категории отделки выбрать из `Finishing_Materials_Catalog` материал, удовлетворяющий условиям: `is_available = true`, `room_types` содержит тип помещения, `style_tags` содержит выбранный стиль или совместимый.
3. THE Design_Worker SHALL вычислять Real_Estimate как сумму четырёх компонент: стоимость материалов = Σ (площадь поверхности категории × `price_per_unit_kopeks`); стоимость мебели = Σ цен подобранных SKU из Requirement 10; стоимость работ = площадь помещения × коэффициент стоимости работ для города пользователя; прочие расходы = фиксированный процент (≤ 10%) от первых трёх.
4. THE Design_Worker SHALL хранить коэффициент стоимости работ для каждого города в существующей таблице `cities` или новой связанной таблице (точная схема определяется в дизайн-фазе) и SHALL использовать общероссийский коэффициент по умолчанию, если у пользователя не указан город.
5. THE Design_Worker SHALL заполнять поле `designs.estimate` массивом из 4 строк (`Отделочные материалы`, `Мебель`, `Работы`, `Прочие расходы`) с суммами в копейках, как уже использует существующий `DesignBoard.tsx`.
6. THE Public_Page SHALL отображать в смете итоговую сумму с пометкой «ориентир по средним ценам» и SHALL ссылаться на источник цен (партнёрский магазин для мебели и материалов, городской коэффициент работ).
7. WHEN все четыре компоненты Real_Estimate (отделочные материалы, мебель, работы, прочие расходы) равны нулю — например, при нулевой площади и пустом подборе мебели — THE Design_Worker SHALL устанавливать итоговую сумму ровно в 0 копеек без минимального порога, и THE Public_Page SHALL отображать её как «0 ₽» без замены на значение по умолчанию.

### Requirement 12: Извлечение Color_Palette из Hero_Render

**User Story:** Как пользователь, я хочу видеть цветовую палитру проекта из 5 цветов, чтобы быстро понять основные тона.

#### Acceptance Criteria

1. WHEN Hero_Render готов, THE Design_Worker SHALL извлечь из него ровно 5 доминантных цветов через существующий модуль `lib/colorExtraction.ts`.
2. THE Design_Worker SHALL записывать палитру в поле `designs.color_palette` в формате массива объектов `{hex}` (имя оставлять опциональным, как в существующей схеме `DesignColorSwatch`).
3. THE Public_Page SHALL отображать палитру в блоке «Цветовая палитра», как уже реализовано в `DesignBoard.tsx`.
4. IF извлечение палитры завершилось ошибкой, THEN THE Design_Worker SHALL продолжить пайплайн без палитры (`color_palette = null`), не блокируя `Design_Project`.

### Requirement 13: Скачивание PDF_Document

**User Story:** Как пользователь, я хочу скачать готовый дизайн-проект одним PDF-файлом на A4, чтобы показать его подрядчику или сохранить локально.

#### Acceptance Criteria

1. WHEN `designs.status = completed` AND нет других условий, временно скрывающих кнопку (в частности, идёт повторный рендер `PDF_Document` или сработала ветка ошибки рендера из пункта 6), THE Public_Page SHALL отображать кнопку «Скачать PDF». IF одно из таких условий активно, THEN THE Public_Page SHALL не отображать кнопку до снятия условия, даже если `designs.status` остаётся `completed`.
2. WHEN пользователь нажимает «Скачать PDF», THE API_Server SHALL вернуть `PDF_Document` в формате A4 портрет с поддержкой кириллицы.
3. THE PDF_Document SHALL содержать секции в фиксированном порядке: обложка с h1 и Hero_Render, параметры проекта, `Top_Down_Plan` с размерами, `Isometric_Render` с выносками, 6 ракурсов, цветовая палитра, отделочные материалы, смета, дизайн-решения, подобранная мебель из `Furniture_Catalog`.
4. THE PDF_Document SHALL быть собран `PDF_Renderer` либо во время первой загрузки (с кэшем в R2 на запись), либо как фоновый шаг Generation_Pipeline; конкретный момент рендера определяется в дизайн-фазе.
5. WHEN `PDF_Renderer` уже сгенерировал документ для данного `Design_Project` ранее, THE API_Server SHALL отдавать кэшированный файл из R2 без повторного рендера.
6. IF `PDF_Renderer` завершился ошибкой, THEN THE Public_Page SHALL отображать на месте кнопки сообщение «PDF временно недоступен, вся информация есть на странице» и SHALL не блокировать просмотр `Design_Project` (см. Requirement 14.4).
7. THE PDF_Document SHALL ссылаться на `Public_Page` (`/dizajn/{slug}`) на обложке и в нижнем колонтитуле каждой страницы.

### Requirement 14: Отказоустойчивость и частичная деградация

**User Story:** Как владелец продукта, я хочу, чтобы поломка одного шага Generation_Pipeline не превращалась в полную потерю проекта, чтобы пользователь всё равно получил полезный результат, а потраченные на проект AI-вызовы не списывались впустую.

#### Acceptance Criteria

1. THE Design_Worker SHALL различать обязательные и опциональные шаги Generation_Pipeline: обязательные — `Layout_JSON`, Hero_Render, AI-текст (h1/seoTitle/description), `Real_Estimate`; опциональные — отдельные Angle_Render помимо Hero_Render, `Top_Down_Plan`, `Isometric_Render`, `Color_Palette`, подбор мебели, `Infographic`, `PDF_Document`.
2. IF любой опциональный шаг завершился ошибкой после допустимых повторов, THEN THE Design_Worker SHALL продолжить остальные шаги, оставив соответствующее поле в `designs` пустым.
3. WHEN все обязательные шаги выполнены успешно (без ошибок после допустимых повторов), THE Design_Worker SHALL устанавливать `designs.status = completed`, даже если часть опциональных шагов не выполнилась. IF любой обязательный шаг завершился ошибкой после допустимых повторов — даже если другие обязательные шаги выполнились успешно — THEN THE Design_Worker SHALL устанавливать `designs.status = failed` и SHALL не переводить запись в `completed`.
4. WHILE один или несколько опциональных артефактов отсутствуют, THE Public_Page SHALL рендерить только те блоки, для которых артефакты есть, и SHALL не показывать пустые секции.
5. THE Design_Worker SHALL отслеживать суммарную стоимость AI-вызовов на один `Design_Project` через существующую таблицу `design_generations` и SHALL прерывать пайплайн со статусом `failed` и `error_message = "превышен бюджет генерации"`, если суммарная стоимость превысила Cost_Ceiling.
6. WHEN обязательный шаг завершается ошибкой после допустимых повторов, THE Design_Worker SHALL устанавливать `designs.status = failed` с описанием конкретного шага в `error_message`.
7. THE Design_Worker SHALL логировать ошибку каждого шага с `design_id`, названием шага, текстом ошибки и стоимостью на момент сбоя.

### Requirement 15: Поддержка Showcase_Project в модели данных

**User Story:** Как владелец продукта, я хочу, чтобы существующая модель данных `Design_Project` без изменений поддерживала и пользовательские проекты из формы, и редакторские образцы (50 заранее заготовленных), чтобы не вводить отдельную таблицу для будущей админ-курации.

#### Acceptance Criteria

1. THE таблица `designs` SHALL различать два режима владения через существующее поле `anon_id`: значение IS NOT NULL для проектов, созданных через `Design_Form`, и значение IS NULL для `Showcase_Project`.
2. THE Design_Worker SHALL обрабатывать одинаково обе категории записей в статусе `generating`, не делая различия между пользовательскими и редакторскими проектами на уровне Generation_Pipeline.
3. THE Public_Page SHALL отображать `Showcase_Project` без пометки «ваш проект» (Requirement 4.4) и без блока «мои дизайны» в навигации, при этом со всеми остальными секциями (ракурсы, план, мебель, материалы, смета и т. д.).
4. THE API_Server SHALL предоставлять отдельный административный эндпоинт для создания `Showcase_Project` с возможностью передать вручную заполненные текстовые поля (h1, description, materials, estimate, solutions), которые тогда не перегенерируются AI_Content_Provider в `Design_Worker` (как уже реализовано через `hasSeedContent`-ветку).
5. WHILE текущая фаза MVP активна, THE админский эндпоинт создания `Showcase_Project` SHALL быть отключён через feature-flag, и операторская курация 50 образцов SHALL не выполняться, оставаясь задачей последующей итерации.

## Decisions

Все локальные открытые вопросы зафиксированы. Значения ниже считаются обязательной частью требований.

**Q1. Платность AI_Design_Product на MVP.**
Бесплатно. Платежная интеграция, тарифы (490 / 990 / 1990 ₽) и провайдер платежей (вероятно YooKassa) добавляются отдельной фичей после валидации спроса и в этом спеке не описываются.

**Q2. Поставщик капчи.**
Cloudflare Turnstile или hCaptcha. Конкретный выбор и интеграция — задача дизайн-фазы.

**Q3. Лимиты Rate_Limiter на сутки.**
По IP — 5 успешных созданий в сутки; по `Anon_Id` — 3 успешных созданий в сутки. Превышение даёт 429.

**Q4. Минимальные размеры комнат.**
`bedroom` ≥ 6 м², `kitchen` ≥ 4 м², `bathroom` ≥ 2 м², `living_room` ≥ 8 м², `hallway` ≥ 1.5 м², `nursery` ≥ 6 м², `apartment` ≥ 18 м². Меньшие площади отвергаются до AI-вызовов.

**Q5. Ограничение размеров комнаты в форме.**
Ширина и длина 200–800 см, высота 220–350 см.

**Q6. Поведение Geometric_Validator при невалидном Layout_JSON.**
Не более 2 повторов запроса AI с описанием нарушений; при дальнейшей неудаче — `failed`, AI_Image_Provider не вызывается.

**Q7. Минимальная ширина прохода.**
60 см между мебелью и от двери к функциональным предметам помещения.

**Q8. Покрытие типов помещения на MVP.**
Только `bedroom`. Остальные типы видны в `Design_Form` как «скоро» и недоступны для отправки. Бэкенд (валидация, шаблоны `Top_Down_Plan`, выноски `Isometric_Render`) реализован в полном объёме только для `bedroom`.

**Q9. Объём Furniture_Catalog на MVP.**
100–200 SKU, тип помещения `bedroom`. Парсер магазинов (Hoff / Leman PRO / Divan.ru / Lazurit) — отдельная фича в будущем, не в этом спеке.

**Q10. Идентичность 6 ракурсов между собой.**
Hero_Render — text-to-image; 5 Angle_Render — edit-image с reference = Hero_Render. Провайдер edit-image выбирается в дизайн-фазе на основании пилота FLUX Kontext Pro vs gpt-image-1.5 edit и фиксируется в env-переменной.

**Q11. Cost_Ceiling.**
$0.30 USD на один `Design_Project`. При превышении — `failed`.

**Q12. Что делать, если опциональный шаг сломался.**
Продолжать пайплайн, оставлять поле пустым, на странице не показывать соответствующий блок. К обязательным относятся `Layout_JSON`, Hero_Render, AI-текст, `Real_Estimate`.

**Q13. PDF_Document — момент рендера.**
Решается в дизайн-фазе: либо последний шаг Generation_Pipeline, либо ленивый рендер при первом нажатии «Скачать PDF» с кэшем в R2. Бизнес-требование одинаково — кэш есть, повторный рендер не нужен.

**Q14. Авторизация.**
Анонимная через `Anon_Id` в cookie `kiro_anon_id`. Yandex OAuth — отдельная фича в будущем.

**Q15. Email-уведомления.**
Не делаем на MVP. Нет писем о готовности проекта, нет рассылок.

**Q16. Showcase_Project на MVP.**
Заморожен. Модель данных поддерживает оба режима, админский эндпоинт создания закрыт feature-flag-ом, операторская курация 50 образцов — задача отдельной итерации.

**Q17. UGC «реальные результаты».**
Существующая placeholder-секция в `DesignBoard.tsx` остаётся placeholder-ом. UGC-загрузка — отдельная продуктовая линия и в этом спеке не описывается.
