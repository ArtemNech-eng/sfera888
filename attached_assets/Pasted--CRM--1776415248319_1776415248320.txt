Создай в CRM новый модуль:
«🧠 Центр контроля мастеров»

ВАЖНО:
В переписках нет сообщений клиентов.
Есть только:
— сообщения мастера
— сообщения ИИ-диспетчера
— сообщения админа

То есть это не анализ клиентских чатов,
а контроль коммуникации с мастерами
по активным заказам.

Модуль должен масштабироваться
на 1000–2000 мастеров и тысячи диалогов.
Поэтому нельзя на каждой странице
заново анализировать все сообщения.
Нужен фоновый расчёт, кеш и карточки-кейсы.

====================================
1. БАЗОВАЯ ИДЕЯ МОДУЛЯ
====================================

Создай сущность:
chat_cases (кейсы контроля)

Один кейс = один активный заказ,
привязанный к конкретному мастеру.

Даже если у мастера один общий чат в Max,
в системе должны быть отдельные кейсы
по каждому его заказу.

Для каждого кейса хранить:

— id
— order_id
— master_id
— city
— district
— service_type
— order_status
— current_stage
— risk_level
— risk_reason
— summary
— next_action
— next_action_deadline
— last_master_message_at
— last_ai_message_at
— hours_without_contact
— hours_without_estimate
— hours_without_payment
— expected_revenue
— expected_commission
— tags (массив)
— confidence (уверенность привязки)
— is_resolved
— created_at
— updated_at

====================================
2. ПРИВЯЗКА СООБЩЕНИЙ К ЗАКАЗАМ
====================================

Так как чат с мастером может быть один,
а заказов несколько, реализуй механизм привязки.

Логика привязки:

1. Если сообщение мастера пришло
   как ответ на исходящее сообщение
   ИИ-диспетчера по конкретному заказу,
   привязать к этому order_id.

2. Если в тексте есть номер заказа
   формата #123 или Заказ 123,
   привязать к order_id.

3. Если номер не найден,
   привязать к самому свежему
   активному заказу этого мастера
   со статусами:
   — мастер назначен
   — на замере
   — смета отправлена
   — ждём оплату
   — в работе

4. Если у мастера 2+ активных заказа
   и нет явной уверенности,
   поставить confidence = low
   и тег:
   ambiguous_order_link

5. Такие кейсы показывать админу
   во вкладке «Нужно уточнение».

====================================
3. СТАДИИ КЕЙСА
====================================

Для каждого кейса вычислять current_stage:

— assigned            = мастер назначен
— waiting_estimate    = ждём смету
— waiting_payment     = ждём предоплату
— in_progress         = в работе
— waiting_update      = давно нет обновлений
— payment_issue       = вопрос по комиссии/оплате
— possible_bypass     = подозрение на обход
— conflict            = конфликт / негатив
— completed           = завершён
— cancelled           = отменён

====================================
4. РИСК-МОДЕЛЬ
====================================

risk_level:
— green
— yellow
— red

Правила:

GREEN:
— заказ движется по срокам
— мастер отвечает
— смета отправлена вовремя
— оплата идёт
— обновления есть

YELLOW:
— нет ответа мастера > 12 часов
— нет сметы > 24 часов после назначения
— нет оплаты > 24 часов после отправки сметы
— по заказу в работе нет обновлений > 2 дней
— мастер пишет «завтра», «позже», «не успеваю»

RED:
— нет сметы > 48 часов
— нет оплаты > 48 часов
— нет обновлений по активному заказу > 4 дней
— есть фразы с риском обхода
— есть негатив / конфликт
— заказ завис > 14 дней

====================================
5. ТЕГИ И СЕМАНТИКА
====================================

Автоматически ставить теги по сообщениям мастера.

Если встречаются фразы:
— напрямую
— без приложения
— без брони
— без предоплаты
— договоримся сами
— скинь номер
— оплата потом
— потом закрою
— клиент не хочет через приложение
— сделал без сметы
— переведу позже
— нет денег
— не успеваю
— завтра сделаю
— позже отправлю
— клиент молчит
— клиент передумал
— дорого
— не буду делать
— конфликт
— жалоба
— претензия

ставить теги:
— possible_bypass
— delayed_estimate
— delayed_payment
— master_delay
— client_refused
— conflict
— no_money
— ambiguous_status

Если есть теги:
possible_bypass или conflict,
risk_level минимум red.

====================================
6. СВОДКА ПО КЕЙСУ
====================================

Для каждого кейса формировать summary
не как полный чат, а как короткую выжимку
на 1–3 предложения.

Пример:
«Мастер назначен 26 часов назад,
смета ещё не отправлена.
Вчера в 18:42 мастер написал,
что отправит вечером.
Риск: средний, нужен контроль.»

Или:
«Смета отправлена 2 дня назад,
предоплата не поступила.
Мастер дважды напоминал клиенту.
Риск: повышенный, решить —
ждать или вернуть в пул.»

Summary обновлять:
— только при новых сообщениях
— только для изменившегося кейса
— не пересчитывать все кейсы разом

====================================
7. NEXT ACTION
====================================

Для каждого кейса автоматически
вычислять next_action:

Возможные значения:
— remind_master_estimate
— remind_master_payment
— ask_master_status
— call_master
— review_for_reassign
— review_for_cancel
— no_action

И next_action_deadline:
дата/время когда стоит вмешаться.

Примеры:
— «Напомнить про смету до 18:00»
— «Проверить оплату завтра в 10:00»
— «Нужен звонок мастеру сегодня»

====================================
11. ДЕЙСТВИЯ ПО КЕЙСУ
====================================

Кнопки:

[💬 Написать мастеру]
— открыть окно шаблонного сообщения

[📞 Позвонить мастеру]
— показать телефон мастера
— кнопка call
(если телефон доступен админу)

[📋 Открыть заказ]
— переход в карточку заказа

[📜 Открыть чат]
— открыть полную переписку
с мастером по этому кейсу

[✅ Отметить как проверено]
— скрыть из красных/жёлтых
на 12 часов, но не архивировать

[🔄 Вернуть на пересмотр]
— пометить кейс как review_required

====================================
12. ШАБЛОНЫ СООБЩЕНИЙ
====================================

Кнопка «Написать мастеру» должна давать
готовые шаблоны по next_action.

Шаблон: смета
«{имя_мастера}, добрый день.
По заказу #{order_id} 
ещё не отправлена смета.
Пожалуйста отправьте её через приложение сегодня.
Без сметы заказ не двигается.»

Шаблон: оплата
«{имя_мастера}, по заказу #{order_id}
предоплата ещё не закрыта.
Проверьте статус и дайте обратную связь.»

Шаблон: статус
«{имя_мастера}, подскажите статус
по заказу #{order_id}.
Когда будет следующий шаг?»

Шаблон: риск обхода
«{имя_мастера}, напоминаю:
все заказы ведём только через систему,
со сметой и предоплатой через приложение.
Подтвердите пожалуйста текущий статус
по заказу #{order_id}.»

Все сообщения отправлять в Max.

====================================
13. ПРАВИЛА ПО СРОКАМ
====================================

Автоматически считать:

hours_without_contact =
текущее время - max(last_master_message_at, last_ai_message_at)

hours_without_estimate =
если статус заказа до сметы,
то от назначения мастера до текущего времени

hours_without_payment =
если смета отправлена, но оплаты нет,
то от даты отправки сметы

days_without_progress =
от последнего изменения статуса заказа

====================================
15. ПРОИЗВОДИТЕЛЬНОСТЬ
====================================

Это критично.

НЕ анализировать все чаты
при каждом открытии страницы.

Сделай так:

— фоновая задача каждые 5 минут
— обновляет только активные кейсы
— пересчитывает summary, risk,
  next_action только для изменившихся кейсов

На странице использовать готовые данные
из таблицы chat_cases.

Добавить пагинацию:
по 50 кейсов на страницу.

Добавить индексы:
— order_id
— master_id
— risk_level
— current_stage
— updated_at
— next_action_deadline

====================================
16. АРХИВ
====================================

Если заказ завершён или отменён:
— кейс переносится в архив
— хранится 90 дней
— доступен во вкладке «Архив»

====================================
17. ДИЗАЙН
====================================

Стиль:
— белый фон
— зелёный акцент
— жёлтый для attention
— красный для critical

Summary должен быть заметным:
карточка внутри строки
с коротким текстом.

Теги — как маленькие бейджи:
possible_bypass
delayed_payment
delayed_estimate
master_delay
conflict
client_refused
ambiguous_order_link

====================================
18. ВАЖНО
====================================

Не делать автопереназначение
и не отменять заказы автоматически.

Модуль:
— анализирует
— помечает
— рекомендует
— уведомляет
— даёт кнопки действий

Решение принимает только админ.
